# Local tutor v1

The experiment asks whether one teaching agent can form increasingly useful, falsifiable theories about a learner from code-review decisions, explicit uncertainty, and optional learner feedback. The app controls evidence and timing; the agent chooses the curriculum. There is no fixed subject taxonomy or learner score.

## One planning cycle

1. Read current interests, recent answered lessons, unchanged predictions, raw answers, working hypotheses, and concept/variant memory reconstructed from the full archive. Include older lessons when current hypotheses cite them. Flagged and accidental answers are excluded from ability evidence, but still count as exposure. IDK records uncertainty without a correctness grade. Read optional notes, conversations, and recorded review exposure alongside answers.
2. Reflect on surprises. Save observations, tentative interpretations, and next actions separately from original question intentions. Revise concept descriptions, representation familiarity, prerequisites, uncertainty, and possible next directions using real evidence. Compare frontier options and explain the chosen mix of teaching and investigation.
3. Produce a complete lesson: objective, assumptions, reflection, hypotheses, curriculum updates, exercises, tests, predicted success probabilities, and expected implications of correct, incorrect, or IDK responses. Each question has separate educational and investigative objectives, multiple purposes, a stage, cognitive demand, prerequisites, scaffolding, and a variant decision.
4. Validate structure, evidence references, curriculum consistency, progression, mirror limits, and every executable fixture. A failure permits one complete repair. No valid batch means no published exercises.
5. Write the full plan to a new read-only file and hash it before exposing the first card. Never revise its predictions after an answer.
6. Record each answer exactly once and immediately show the next card. Explanations, counterexamples, and predictions appear only when the learner opens a review. At the end, accept optional notes and accidental-answer exclusions before the next planning cycle.

This is intentionally a single bounded agent call plus an optional repair, not a general agent framework. The local server provides context retrieval, validation, persistence, and progress. The CLI only produces structured lesson or conversation responses and cannot run arbitrary tools. There is no background model use. The learner explicitly requests each lesson or optional conversation response. Review exposure can affect later probes. The prompt receives review openings and estimated foreground viewing time, and must not assume every explanation was read. Viewing time does not prove attention or understanding. Old answers without telemetry have unknown review exposure.

## Curriculum planning

Concept definitions use stable IDs and names with revisable descriptions, representations, prerequisites, evidence, and uncertainty. Memory is reconstructed from all sealed plans and linked answers, independently of the recent lesson window. Unmentioned concepts persist. Generated cards and deferred variants do not count as learner exposure. Familiarity is a tentative description, not a mastery score: a new `familiar` claim requires at least three cited correct judgments across two lessons, and exclusions retract unsupported claims. This threshold is a conservative bookkeeping rule, not evidence of mastery. Recent evidence summaries retain counterexamples as well as supporting citations. Legacy cards can receive tentative retrospective concept annotations without changing their original artifacts. Baseline definitions cannot overwrite an earlier reflective assessment.

New batches include teaching, investigation, transfer, and both correct and buggy implementations. The required order is warmup → build → optional stretch → consolidation. Opening demand is at most 2 on a relative 1–5 scale; it cannot jump by more than one; a context switch may lower demand to introduce a simpler bridge. Stretch cards appear in the second half, with a rationale for preparation, support, diagnostic intent, or reasonable exploration. A successful scaffolded question can provide supporting evidence for readiness and familiarity, while its support remains visible and is not counted as an independent success. Earlier questions that meaningfully exercise a prerequisite provide preparation, not proof of learning. Consolidation holds or lowers demand. Predictions stay independent of these demand labels. Neither the labels nor the checks establish actual learner difficulty or mental energy; explicit pacing feedback informs the next batch, and the current batch stays fixed.

A task family identifies related correct/buggy variants. By default only one is asked, with the counterpart deferred or left unasked and a reason saved. At most one two-card mirror family is allowed in a lesson, only during build/consolidation to introduce concepts with no prior exposure. Both cards must declare the same family/concepts, opposite verdicts, and an introduction purpose. A family already encountered cannot become a new same-lesson pair. Shared specifications, identical reference tokens, and conservative near-duplicate heuristics catch undeclared mirrors; this is not a proof of semantic equivalence. Memory records which implementation verdicts were actually shown so a later counterpart can close a deferral. The reference implementation alone never counts as another asked card.

These checks enforce a planning contract. They cannot establish that purposes are sincere, that scaffolding teaches effectively, or that an interpretation follows from the evidence. Completed lessons reveal saved intentions, frontier choices, and later observations in the notebook. Planning metadata remains hidden during a lesson because it can identify a later mirror's verdict.

## Data and accountability

`state.json` contains settings, lessons, answers, lesson feedback, review sessions, and optional tutor conversations. Existing version-1 notebooks load without modifying sealed plans or original answers. `plans/<id>.json` contains each immutable full lesson; SHA-256 covers the entire artifact, including fixtures and predictions. Startup verifies these files match. `state.backup.json` holds the previous state write. `runs/<id>.json` records planning status without CLI logs or credentials. State replacement is atomic. Do not run two servers with the same data directory.

Evidence IDs must identify real, unflagged answers. A supported claim needs supporting evidence; a contradicted claim needs counterevidence. New hypotheses remain tentative. These checks prevent fabricated citations, but do not prove that the interpretation follows from the evidence. The learner can inspect the notebook and flag defective questions.

The reflective prompt uses up to 12 recent lessons plus older evidence cited by current hypotheses, subject to a 280 KB context budget. Oldest lessons are omitted first when necessary, and current hypotheses lose citations to omitted evidence rather than inventing support. All history remains in the local archive. Baseline mode gets interests and batch size with no history, hypotheses, or historical metrics. It still commits predictions and passes identical validation. Switching modes is exploratory, not a randomized study: familiarity and provider differences can confound comparisons.

Brier score is the mean of `(pCorrect - actualCorrect)^2`; lower is better. Calibration bins compare predicted and observed success. Metrics exclude flagged attempts and IDK responses, and are scoped by provider and mode across all contexts. The resulting score describes answered judgments, not abstention behavior; changing how often the learner uses IDK can change the sample. Small samples are noisy. A lower Brier score does not establish better teaching: easy, familiar exercises can be predictable. Purposes are tracked separately; a question can contribute to multiple purpose categories but is counted once overall. Retention requires related evidence at least 24 hours old, including evidence preserved in concept memory; the app cannot establish a causal learning benefit from these labels.

Review sessions use cumulative, idempotent durations so retried requests cannot double-count time. The browser pauses its clock when the tab is hidden or the window loses focus. It periodically flushes progress and keeps a local retry queue for interrupted connections, preserving the browser's original opening timestamp even if delivery is delayed. A crash before the next flush can still lose a little time. Lesson notes are untrusted learner reports, not an oracle for exercise validity. Marking an accidental answer excludes it without rewriting the original judgment; removing that annotation does not undo an independent flawed-question flag.

## Optional lesson conversations

After completing a lesson, the learner can share any feedback and explicitly request a tutor response. The same isolated Codex/OpenCode runner returns a short reflection and zero to three optional questions. Responses are validated for shape and length and saved separately from sealed lesson plans. Each exchange preserves the feedback shared at that time, the tutor's reflection, replies, and explicit skips. Reply drafts survive a browser refresh; submitting or starting the next lesson saves them. Blank replies are skipped, and continuing cancels any pending discussion call before planning. A late cancelled response cannot publish.

The next reflective plan includes recent conversations, bounded to 12 exchanges and roughly 48 KB. It must reconsider assumptions using learner feedback while distinguishing self-reports from demonstrated capability. Earlier tutor reflections are tentative interpretations, not independent evidence. Skipping follow-ups is not negative evidence. Old grades and predictions remain unchanged. The learner may request another response using **Update tutor**; there is no automatic chain of questions or requirement to participate. Baseline mode omits conversations and does not offer personalized discussion. Demo responses are scripted.

## Knowledge, contexts, and graph history

Concept definitions, contextual learner assessments, learning contexts, relationships, and execution environments are separate records. The agent grows concepts and contexts from goals and evidence; app-maintained environment definitions control execution. Language is rendering/runtime metadata, not the curriculum boundary. Context parents do not inherit evidence or runtime access. A general concept can link to a distinct contextual API concept through specialization or application relationships.

`curriculum.knowledge` holds concept/context definitions, relationship revisions, contextual assessments, and proposed equivalent-concept merges. Each card and skill attribution records its context. `contextPractice` replaces language-only summaries and reconstructs full-archive evidence, with supporting, challenging, incidental, scaffolded, and retrospective distinctions. Familiarity requires citations in the same context; cross-context successes guide hypotheses rather than satisfying that requirement. Unverified responses have the same evidential eligibility. Exclusions retract evidence consistently.

Identity aliases and relationship revisions have an append-only audit history. New draft references are canonicalized before commitment; historical references resolve through a reversible overlay. A merge never rewrites old plan files. Undo rebuilds evidence from original references, deduplicating observations by attempt/concept/context. The searchable Notebook view reveals completed assessments, not hidden planning details from unfinished lessons.

Reflective planning supplies a relevant graph neighborhood, older alternatives, a compact identity index, and bounded contextual evidence. Baseline planning gets the built-in context catalog and no personal graph or history. Up to two contexts may appear in one coherent lesson. Preparation is explained in the plan; missing prerequisite success is not a publication gate. A context switch can lower demand for a bridge while preserving stage order, gradual increases, late optional stretch, and final consolidation.

Notebook version 2 adds graph metadata without changing sealed lessons. Startup verifies all plan hashes before migration, backs up state and plan files, maps historical languages to contexts, and reconstructs assessments from eligible evidence. `npm run migrate:knowledge -- --data-dir PATH` previews the migration; `--apply` performs it with the server stopped. It is idempotent. Single-language clients remain supported for settings and guide/practice requests through compatibility mapping.

## Execution boundary

The app supports pure synchronous JavaScript, Python, and Rust functions with JSON-compatible fixture data. Missing language metadata on sealed older lessons means JavaScript; those artifacts are never rewritten. New questions declare a descriptive `signature` with a function name and ordered parameter names. Each fixture's `inputJson` encodes the positional argument array: `sumReadings(readings)` receives `[[1, 2]]`, while `lastLowStockIndex(counts, threshold)` receives `[[4, 1, 3], 2]`. Candidate and reference declarations must match the signature and share conventional documentation: JSDoc for JavaScript, a Python docstring, or Rust `///` comments. Input constraints belong in that documentation; natural task descriptions explain behavior. Legacy sealed JavaScript questions without a signature still execute as `solve(input)`.

For JavaScript, each fixture runs in a fresh QuickJS WASM runtime with a memory limit and execution deadline. Every argument is deeply frozen. The harness captures its invocation and serialization helpers before loading generated code. No Node, filesystem, network, module loader, clock, random source, or host callbacks are exposed. The reference must pass all fixtures. A candidate labeled correct must pass all; a candidate labeled buggy must have a real mismatch or runtime exception. Timeouts and harness failures reject the exercise instead of counting as evidence of a bug.

Historical presentation revisions are appended separately to the local record. Each references the original lesson hash and maps old fixture inputs to the new argument list. Import checks the archive fingerprint and compares original/revised candidate and reference results on every saved fixture; it never changes expected outputs, verdicts, or predictions. Historical review applies the revised presentation and exposes the original alongside it. Learner modeling continues to use the original questions the learner actually answered. Wording and full semantic equivalence still require manual review; fixture agreement alone is insufficient.

## Concept guides and focused practice

The app presents an optional preview when a committed lesson introduces or explores a concept with unknown familiarity. Guides are separate from model hypotheses and are reusable by concept ID. A small reviewed set is available immediately; other guides are generated on demand with the configured CLI. Generated examples can be pure expressions or multiline snippets that assign a JSON-compatible value to `result`; both are checked when the context has a supported execution environment; other contexts use explicitly unverified illustrations. Guides are keyed by concept and learning context; links are selected from official documentation, not generated by the model. Execution verifies the example result, not the accuracy of the surrounding explanation.

Guide opens, explicit completed readings, and optional familiarity reports are timestamped events. They represent exposure or self-report, not demonstrated knowledge. Focused practice is a four- or six-question sealed lesson targeting the selected concept; it pauses the active parent lesson, excludes duplicates of unanswered parent questions, and restores the parent after completion or early exit. A restart preserves the active lesson. Partial practice answers remain in the history when practice is left early. Normal lesson size settings stay unchanged. The tutor receives recent guide events and focused-practice history so it can interpret answers in context. Answer reviews identify study or focused practice that occurred after a parent's original predictions and before that answer; the predictions themselves never change.

Python uses a pinned Docker image and a separate disposable container for each fixture and source. The container has no host mounts or network, runs as an unprivileged user with capabilities dropped, a read-only root filesystem, and CPU, memory, process, and execution-time limits. Only a small set of standard-library imports is supported. The runner receives source and one input, never the expected result. It checks Python syntax, signature and docstrings and rejects invalid outputs or resource failures; exceptions and observed input mutations can be counterexamples. Mutation checks compare inputs before and after the call, so mutations that are completely undone are not detected. Docker and the image must already be available; the app never falls back to unsandboxed host Python. The Python process and container boundary are distinct from the QuickJS sandbox and depend on Docker’s isolation being correctly configured.

Rust uses a pinned Docker compiler image with the same network, privilege, resource, and host-mount restrictions; it uses a bounded temporary filesystem to compile. The reference and candidate are each compiled in their own disposable container, and each fixture runs in a fresh process. Expected outputs stay outside the container. Inputs support scalar values, strings, vectors, immutable slices and references, `Option`, `Result`, and string-keyed `HashMap` values; outputs support the corresponding JSON-compatible values. Nested `Option<Option<T>>` is excluded because its states are ambiguous in the fixture format. Both candidate and reference must compile. A candidate labelled buggy must fail a fixture or panic. Compilation failures, timeouts, and harness errors reject the draft and reach the repair loop; they cannot be published as compiler-only exercises. Historical compiler diagnostics remain readable. No packages, custom structs, mutable reference arguments, or arbitrary compiler execution on the host are supported.

Expected results and reference code come from the same agent. Execution catches contradictions and concrete bugs; it cannot prove alignment with the written specification or exhaustive correctness. The app avoids arbitrary runtimes and package installation. Unsupported contexts can produce code or proposed-answer cards with a committed model-supplied verdict and explanation. These use the same grading, evidence rules, and metrics. Their review records that no independent verification occurred, with no fabricated checks. The verification path is selected before validation; failed executable tasks cannot be downgraded during repair. More independent/property-based oracles, held-out assessments, and delayed follow-up sessions would strengthen a later experiment.

## Providers

Codex runs with ephemeral sessions, read-only sandboxing, a strict output schema, and tool/plugin/instruction discovery disabled. A version preflight rejects Codex older than 0.153.4 before making a model request; the app never silently drops isolation options for an older executable. `CODE_SWIPE_CODEX_BIN` can select a supported installation when the server inherits a different PATH from the terminal. OpenCode uses a dedicated temporary config/session directory and denies all tools while retaining existing authentication. Both run without a shell, with bounded output, a deadline, and cancellation. Temporary files are removed afterward. Errors distinguish unsupported options, schema incompatibility, authentication, limits, network failures, and process exits without exposing raw CLI logs. A normal provider error does not silently substitute demo data.

The default per-call deadline is six minutes for lessons and three minutes for optional conversations; a repair may use another call. Cancellation kills the child process group on Linux/macOS. Windows only guarantees termination of the direct CLI process. Model output and validation reports are checked before publication. Only local requests can trigger planning; the HTTP server checks Host, Origin, request type, and browser cross-site metadata.

To start a separate experiment without altering an existing notebook, set `CODE_SWIPE_DATA_DIR` to a new directory. The old data remains available by pointing back to it. No migration from the previous Firebase-based version is included.
